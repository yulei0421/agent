# 知乎文章系列设计：从 Agent 工程实践到金融研究产品

## 目标

基于项目当前 `README.md` 和已经落地的代码能力，撰写三篇可独立阅读、又能组成完整系列的知乎文章。文章面向对 AI Agent 工程、LangGraph、TypeScript 全栈以及金融研究产品感兴趣的开发者和产品人员。

每篇文章控制在约 2500～3500 字，使用第一人称实战语气。内容不照抄 README，不夸大项目能力，不披露 API Key、用户目录等敏感信息。

## 系列关系

三篇文章采用递进式结构：

1. 第一篇回答“为什么要改，以及演进过程中遇到了什么问题”。
2. 第二篇回答“这套 Agent 架构具体如何实现”。
3. 第三篇回答“这些工程能力最终组成了怎样的金融研究产品”。

三篇文章可以互相引用，但各自包含必要背景，读者不需要按顺序阅读。重复内容只保留简短回顾，并引导读者阅读对应文章。

## 第一篇：实战复盘

### 标题

《我把写死在代码里的 Agent 路由，改成了模型自主决策》

### 核心读者

- 正在从普通聊天机器人升级到工具型 Agent 的开发者。
- 遇到关键词路由覆盖不足、工具误触发或流程难扩展问题的团队。
- 想了解 LangGraph 在真实项目中承担什么职责的人。

### 核心观点

Agent 的关键不是“接入更多工具”，而是建立一条可控的自主决策链路：

```text
用户消息 + 工具清单
  -> 模型选择工具
  -> 服务端校验并执行
  -> 工具结果回传模型
  -> 模型继续调用或输出最终回答
```

模型负责语义理解和决策，服务端拥有能力边界、参数校验、执行权限与停止条件。LangGraph 负责让 Planner、模型、工具与收敛策略真正参与同一个循环，而不是只生成一个不影响后续执行的装饰性计划。

### 内容结构

1. 从一个天气查询问题切入：为什么关键词路由总有未覆盖问法。
2. 早期方案的问题：业务代码膨胀、规则冲突、扩展成本上升。
3. 关键转折：把工具描述交给模型，但不允许模型生成任意代码。
4. ToolManifest 如何划定服务端执行边界。
5. 为什么仅有工具调用还不够，以及 Planner 曾经“存在但不参与决策”的问题。
6. 接入 LangGraph 后的循环、停止条件和计划可见性。
7. 工程踩坑：SSE 打字机效果、工具事件顺序、`model_unavailable`、Electron 环境变量路径。
8. 复盘：把自主权交给模型，把控制权留在服务端。

### 文章边界

本篇以演进故事和架构取舍为主，不展开每个模块的完整代码，不详细罗列全部金融功能。

## 第二篇：技术教程

### 标题

《用 TypeScript、NestJS 和 LangGraph 搭建一个可控的 AI Agent》

### 核心读者

- 熟悉 TypeScript，希望实现工具调用 Agent 的前后端开发者。
- 想了解 NestJS、LangGraph、SSE 和 Tool Calling 如何组合的人。
- 需要在自主能力与安全约束之间取得平衡的工程团队。

### 核心观点

一个可投入真实项目验证的 Agent，需要同时具备能力声明、模型决策、受控执行、流式反馈、错误收敛和可观测性。LangGraph 是编排层，不应侵入应用层业务接口；工具也不是任意函数，而是带有 schema、风险等级、超时和执行器的部署期能力。

### 内容结构

1. 给出 React、Electron、NestJS、LangGraph、DeepSeek 和外部数据源的总体架构。
2. 定义 ToolManifest：名称、描述、闭合参数 schema、风险等级、超时和执行器。
3. 定义 Agent 状态：消息、计划、当前步骤、工具调用计数和失败摘要。
4. 解释 Planner、模型节点、工具节点和收敛节点之间的数据流。
5. 展示服务端校验、同轮并行执行与结果顺序保持。
6. 通过 SSE 输出 `task`、`plan`、`tool`、`tool_result`、`delta`、`error` 和 `done`。
7. 介绍任务路由、备用模型、首事件超时、重试与熔断。
8. 介绍取消、人工审批、后台任务和 Prometheus 聚合指标。
9. 给出测试策略：类型检查、状态机测试、工具契约测试、SSE 测试和 Electron sidecar 测试。
10. 总结可以复用到其他业务 Agent 的最小架构。

### 示例原则

- 使用经过简化但语义准确的 TypeScript 伪代码。
- 每段代码只解释一个边界，避免大段粘贴项目源码。
- 代码示例不包含真实密钥、内部绝对路径和未经审计的外部 URL。

### 文章边界

本篇重点讲工程实现，不详细讨论金融业务价值，也不写成逐文件源码导读。

## 第三篇：产品与能力展示

### 标题

《一个金融 AI Agent 应该具备哪些能力？这是我的完整答案》

### 核心读者

- 评估金融 AI Agent 产品形态的产品经理、技术负责人和开发者。
- 关注研究流程、数据可信度、引用和安全边界的从业者。
- 希望了解 AI Agent 从聊天框走向桌面研究工作台的人。

### 核心观点

金融 Agent 不能只会生成文字。它需要可靠地获取行情和事件数据，说明数据时间与来源，在需要时拆解研究目标，并将结果转化为可复核、可导出的工作成果。同时，它必须明确不做什么：不伪装实时数据、不生成任意代码、不越权访问网络、不执行交易。

### 内容结构

1. 从“聊天框为什么不等于金融 Agent”切入。
2. 展示五类研究入口和资产上下文。
3. 介绍天气、新闻、资产搜索、报价、技术指标和经济日历六类工具。
4. 介绍研究员与风险复核员的受限分工，以及主 Agent 的统一执行权。
5. 介绍 PDF、图片 OCR、请求级检索和本地有限工作记忆。
6. 介绍引用账本、内容哈希、来源重验证和数据新鲜度。
7. 介绍结构化研究报告及 PDF、PPTX 导出。
8. 介绍后台任务、取消、重试、通知和 Electron 桌面交付。
9. 说明安全边界：只读工具、域名白名单、人工审批、下载链接时效和本地配置。
10. 坦诚列出限制：没有服务端持久化记忆、跨设备会话、持久化任务队列和交易执行。
11. 总结金融 Agent 从 Demo 走向产品仍需要解决的问题。

### 文章边界

本篇不承诺投资收益，不把研究辅助描述为自动交易系统，不把演示数据源描述为生产级授权数据。

## 统一写作规范

### 叙事与表达

- 开头使用具体问题或真实开发场景，不使用泛泛的行业口号。
- 先讲问题和决策，再讲技术名词。
- 使用短段落和清晰小标题，适应知乎移动端阅读。
- 保留必要的技术细节，但每个概念都说明它解决了什么问题。
- 对已经实现、部分实现和仍未实现的能力使用明确措辞。

### 图示与代码

- 第一篇使用一张“硬编码路由到模型自主决策”的演进图。
- 第二篇使用一张系统架构图和一张 LangGraph 循环图。
- 第三篇使用一张金融 Agent 能力分层图。
- 图示先用 Mermaid 或文本图表达，发布时可再转换为图片。
- 每篇最多放置三至五段短代码或配置示例。

### 文件规划

正文保存到以下文件：

- `docs/zhihu/01-agent-routing-to-langgraph.md`
- `docs/zhihu/02-typescript-nestjs-langgraph-agent.md`
- `docs/zhihu/03-financial-agent-capability-map.md`

## 验收标准

- 三篇文章分别覆盖实战复盘、技术教程和产品能力三个角度。
- 每篇约 2500～3500 字，并具有独立的标题、摘要、开场、正文和结尾。
- 技术描述与当前 README 和代码能力一致。
- 三篇之间没有大段重复内容。
- 所有 Markdown 默认使用中文，代码标识符和必要技术名词除外。
- 不出现真实 API Key、个人目录、投资建议或无法由当前项目支撑的能力声明。
