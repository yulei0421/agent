# Codex 风格紧凑聊天输入区设计

## 背景

当前聊天输入区将模型工具说明、人工审批开关、附件入口、本地记忆说明、停止按钮和发送按钮全部作为常驻内容展示。即使用户只想输入一句问题，输入区也会占据较大的垂直空间，消息阅读区被明显压缩，整体交互更接近设置表单而不是连续对话。

本次调整参考 Codex 和常见网页聊天产品的输入交互：默认只展示输入和高频动作，将附件、工具审批及说明信息按需呈现。现有功能和请求协议保持不变。

## 目标

- 将输入区默认高度收敛到约 `104px`，为消息阅读区释放空间。
- 使用单层底部工具栏承载附件、审批状态和发送操作。
- 输入内容增加时自动扩展，达到上限后仅在输入框内部滚动。
- 生成中让发送按钮原位切换为停止按钮，避免同时展示互斥操作。
- 将低频说明改为按需查看，不再占用默认布局高度。
- 保留键盘操作、附件解析、人工审批、金融模式和无障碍状态。
- 桌面端与移动端使用一致的操作模型，不在窄屏退化为多个全宽按钮。

## 非目标

- 不改变聊天 API、SSE 事件、人工审批协议或附件上传协议。
- 不改变消息数据结构、IndexedDB 存储和历史附件召回逻辑。
- 不重做侧栏、金融工作台或消息正文的视觉风格。
- 不新增富文本编辑、拖拽上传、多附件上传或语音输入。
- 不仿制 Codex 的品牌视觉，只参考其输入区的信息层级和交互模型。

## 交互模型

### 默认状态

输入区由两行组成：

1. 可自动增长的文本输入区域。
2. 单层操作工具栏。

工具栏左侧依次提供附件入口和人工审批开关，右侧提供发送按钮。模型工具默认保持自动调用，不再展示独立的“模型工具”标题和常驻说明。

发送按钮使用明确的箭头图标，并提供可访问名称和悬停提示。输入为空、附件仍在解析或正在生成时，发送动作不可用。

### 输入增长

文本输入默认保持紧凑高度。用户输入多行内容时，输入框根据内容高度自动增长，最高约 `200px`；超过上限后输入框内部滚动，输入区不再继续挤压消息列表。

Enter 发送，Shift+Enter 换行。输入法组合输入期间不得误触发发送。

### 附件

附件入口使用工具栏图标按钮和隐藏文件输入。选择文件后，文件名以可移除标签显示在文本区域下方、工具栏上方。解析中显示紧凑状态；错误信息只在发生错误时出现，并使用 `role="alert"`。

本次继续保持一次只选择一个附件，不调整文件类型和大小限制。

### 人工审批

人工审批从常驻说明卡改为工具栏切换按钮：

- 关闭时显示普通工具按钮。
- 开启时显示选中状态，并通过简短标签或提示表达“工具执行前需审批”。
- 点击按钮直接切换模式，不增加二次确认。
- 生成中禁用切换，避免当前请求权限状态与界面状态不一致。

完整说明通过按钮的悬停提示和可访问描述提供，不再占用输入区正文高度。

### 发送与停止

非生成状态显示发送按钮。开始流式生成后，同一位置切换为停止按钮，不同时展示发送和停止。

停止按钮使用方形停止图标、危险操作色和可访问名称。点击后沿用现有 `onStop` 行为。请求结束、失败或停止后恢复发送按钮。

### 消息滚动

聊天面板继续使用“消息列表占剩余高度、输入区位于底部”的网格结构。消息列表是唯一主滚动区域，输入区不随历史消息滚走。

输入区上方增加轻微的背景过渡或遮挡层，防止滚动内容视觉上穿过输入框，但不额外创建大型浮动容器。

## 组件设计

### `ChatWindow`

保留现有消息、流式状态、附件、审批和发送回调。新增仅属于输入体验的本地状态和引用：

- 文本域引用，用于根据 `scrollHeight` 自动调整高度。
- 必要的提示可见性状态；若使用原生 `title` 和 `aria-label` 即可满足要求，则不新增弹层状态。

表单提交和附件转换逻辑保持原有数据流。输入区内部结构调整为：

1. 文本域。
2. 可选的附件状态行或错误行。
3. 工具栏。

不拆分新的全局状态，也不将输入草稿提升到 `App`。

### 图标

项目当前未安装图标库。本次使用一个轻量图标依赖统一提供附件、发送和停止图标，优先采用 Lucide React。不得使用 Unicode 字符或手绘、不一致的 SVG 代替常见操作图标。

每个纯图标按钮必须包含 `aria-label`，并通过 `title` 或现有提示组件解释用途。

### 样式

输入区沿用现有颜色变量和圆角体系，避免建立第二套主题。主要样式变化包括：

- 收紧输入区间距、阴影和默认高度。
- 文本域禁止用户手动拖拽，改为内容驱动增长。
- 工具栏按钮使用固定尺寸，避免状态切换造成布局位移。
- 审批开启、发送可用、停止生成和禁用状态具有清晰差异。
- 移除旧的模型工具说明、审批说明卡、上下文说明和双按钮布局样式。

## 数据流

1. 用户输入内容，文本域根据内容自动调整高度。
2. 用户可选择一个附件；文本附件在浏览器读取，二进制附件沿用现有解析接口。
3. 用户可在非生成状态切换人工审批模式，状态继续由 `App` 管理。
4. 用户提交后，输入文本和附件转换为现有 `ChatDocument`，调用 `onSend`。
5. `streaming` 变为 `true` 后，发送按钮切换为停止按钮，审批和附件入口进入禁用状态。
6. 请求结束后恢复发送状态，文本域回到默认高度。

## 错误和边界状态

- 附件解析失败时保留当前草稿，展示紧凑错误信息。
- 附件解析过程中禁止发送，避免提交不完整文档。
- 输入为空时发送按钮禁用，但附件本身不能作为无文本消息提交，保持现有行为。
- 生成中禁止重复提交、替换附件和切换审批。
- 文本域高度调整不得在服务端渲染环境访问不存在的 DOM；本项目为客户端应用，但实现仍只在事件或 effect 中读取元素尺寸。
- 长文件名必须截断，移除按钮保持可点击。
- 320px 宽度下工具栏不得横向溢出，按钮触控区域不小于 `44px`。
- 减少动态效果偏好开启时，状态切换不使用明显动画。

## 测试策略

### 组件和源码测试

- 保留 Enter 发送、Shift+Enter 换行和输入法组合态测试。
- 覆盖附件入口、附件移除、解析中禁用和错误提示。
- 覆盖审批按钮的开关、选中状态和生成中禁用。
- 覆盖发送与停止按钮按 `streaming` 状态互斥呈现。
- 覆盖纯图标按钮的可访问名称。

### 样式测试

- 断言输入区采用紧凑默认间距和受限最大高度。
- 断言文本域使用自动增长所需样式且不允许手动拖拽。
- 断言移动端工具栏保持单行或合理换行，不恢复双全宽操作按钮。
- 断言消息列表继续独立滚动，输入区位于聊天面板底部。

### 运行时视觉验收

使用 Playwright 在桌面与移动端检查：

- 空输入、长输入、已选附件、审批开启、附件错误和生成中状态。
- 输入区默认高度显著小于调整前，消息内容获得更多可视面积。
- 窄屏不出现重叠、横向滚动或被遮挡的操作按钮。
- 发送、停止、附件和审批均可通过鼠标与键盘操作。

## 验收标准

1. 空输入且无附件时，输入区高度约为 `104px`，不再显示常驻说明和设置卡。
2. 文本输入随内容增长，最高约 `200px`，之后仅文本域内部滚动。
3. 附件、审批和发送位于同一工具栏；已选附件和错误仅在需要时额外占用空间。
4. 发送和停止在同一位置互斥显示，状态切换不引发布局跳动。
5. Enter、Shift+Enter、组合输入、附件解析和审批模式保持现有功能。
6. 消息列表是聊天主区域的唯一滚动容器，输入区始终留在底部可见范围。
7. 320px 以上视口不出现输入区横向溢出，关键触控目标不小于 `44px`。
8. 类型检查、相关自动化测试、生产构建和 Playwright 视觉检查通过。

## 风险与缓解

自动增长文本域可能因内容清空、字体加载或容器宽度变化留下错误高度。实现时在内容变化后统一根据 `scrollHeight` 重算，并在提交清空后恢复默认高度。

引入图标依赖会增加少量前端包体积。只引入按需导出的图标组件，并通过生产构建确认打包结果。

将审批说明收进提示后，可发现性可能下降。审批开启状态必须在工具栏中持续可见，并同时提供 `aria-pressed`、`aria-label` 和提示文本。
